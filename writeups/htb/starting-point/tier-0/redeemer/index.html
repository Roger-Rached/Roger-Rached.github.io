04 — Redeemer.

Very Easy · Linux · Redis

VERY EASY LINUX REDIS DATABASE ENUMERATION UNAUTHENTICATED ACCESS
01 — ENUMERATION

Identifying the Redis service

I began with a targeted Nmap scan to determine whether Redis was exposed and to fingerprint the service version running on the target. 

nmap -p 6379 -sC -sV <TARGET_IP>

Nmap identifying Redis on TCP port 6379.

FINDING 01

TCP port 6379 was open and identified as Redis 5.0.7.

Port 6379 is commonly used by Redis. Seeing a Redis service exposed remotely made authentication and access controls the immediate areas of interest.

Redis is an in-memory data structure server commonly used as a database, cache and message broker. An unnecessarily exposed Redis instance can therefore expose both stored application data and administrative functionality.

02 — SERVICE ANALYSIS

Understanding Redis

Before interacting with the database, I established the basic properties of the service that were relevant to the assessment.

DATABASE TYPE

Redis is an in-memory database.

Redis command-line client

The standard command-line utility used to interact with a Redis server is redis-cli. For remote connections, the -h option specifies the target host. 

redis-cli -h <TARGET_IP>

Redis documents the same connection pattern for remote instances using -h for the endpoint and -p when a non-default port is required. :contentReference[oaicite:2]{index=2}

03 — ACCESS

Connecting to Redis

With Redis confirmed on port 6379, I connected directly using the Redis command-line client. The immediate objective was to determine whether the instance required authentication before allowing database interaction. 

redis-cli -h <TARGET_IP>

Establishing an interactive Redis session with redis-cli.

FINDING 02

The Redis instance accepted the connection without requiring authentication.

This was the key configuration weakness. Remote access to the database interface was available without credentials, allowing direct interaction with the Redis datastore and its available commands.

04 — SERVER ENUMERATION

Inspecting server information

Once connected, I used the Redis INFO command to gather server statistics and environment information. This is useful because database services can disclose details about their version, platform and runtime state before application data is inspected. 

INFO

Redis documents INFO as the command used to return information and statistics about the server. Its output can include details covering the server, clients, memory, persistence, replication and keyspace. :contentReference[oaicite:3]{index=3}

FINDING 03

The server reported:

Linux 5.4.0-77-generic x86_64

redis_version:5.0.7

This confirmed the Linux platform and matched the Redis version identified during the initial service scan.

05 — DATA ENUMERATION

Enumerating Redis keys

With unauthenticated database access established, I moved from server-level enumeration to the datastore itself. Redis organizes stored data around keys, so enumerating the available keyspace was the next logical step. 

KEYS *

In this small lab environment, KEYS * provided a quick way to identify the stored keys. Among the results was a key named flag, giving me a direct target for retrieving the stored value.

Enumerating the Redis keyspace and retrieving the flag value.

Retrieving the flag

I then queried the discovered key using GET, which returns the string value associated with a key. 

GET flag

The command returned the flag, completing the intended attack path.

FINDING 04

An unauthenticated client could enumerate the database keyspace and retrieve the value of the flag key.

Redis documents GET as the command used to retrieve the string value associated with a key. :contentReference[oaicite:4]{index=4}

06 — REDIS PENTESTING

Additional enumeration techniques

Redeemer only required basic Redis access and key/value enumeration. During a broader authorized assessment, however, additional Redis functionality can provide useful visibility into the server and its datastore.

Cursor-based key enumeration 

SCAN 0

SCAN performs cursor-based keyspace iteration. Redis recommends scan-based approaches for larger datasets because commands such as KEYS * can block the server while traversing the keyspace. :contentReference[oaicite:5]{index=5}

Monitoring activity 

MONITOR

The Redis MONITOR command streams commands received by the server in real time. In an authorized assessment, this can help reveal how an application interacts with its datastore.

07 — FURTHER ATTACK SURFACE

Configuration-based attack paths

A Redis deployment can expose a significantly larger attack surface when administrative commands are available, the service runs with excessive privileges, or network exposure is poorly controlled.

Historical Redis attack paths have included abuse of configuration functionality and other administrative capabilities. Whether a particular technique is possible depends on the Redis version, operating-system configuration, process privileges and enabled functionality.

IMPORTANT

These techniques were not required to solve Redeemer. The actual path was: unauthenticated Redis access → server enumeration → key enumeration → flag retrieval.

This distinction matters in a professional assessment: a possible exploitation technique should not be presented as a confirmed vulnerability unless the target configuration has actually been shown to support it.

08 — DEFENSIVE NOTES

Securing an exposed Redis instance

The same configuration issues identified during an assessment can be translated directly into defensive controls. Redis should only be reachable from systems that genuinely require access, while authentication and authorization should be configured according to the deployment's security requirements.

  • Restrict Redis network exposure to trusted interfaces and hosts.
  • Require authentication and appropriately scoped access controls.
  • Run Redis with the minimum operating-system privileges required by the service.
  • Avoid exposing administrative functionality to untrusted clients.
  • Keep the Redis deployment and underlying host software updated and monitored.
09 — WHAT I LEARNED

Lessons from Redeemer

Redeemer reinforced the importance of identifying the technology behind an exposed port before deciding what to test next. Once port 6379 revealed Redis, the assessment became a database-specific investigation rather than a generic service scan.

The critical weakness was the combination of a remotely accessible Redis instance and the absence of authentication. That allowed direct interaction with the database, server information disclosure, key enumeration and ultimately retrieval of the flag.

The machine also demonstrated how effective enumeration can be without relying on a complex exploit. Understanding the service, identifying the access-control failure and following the exposed data path were enough to complete the assessment.

10 — TOOLS & TECHNIQUES

Tools used

The main tools and techniques used during the exercise were:

  • Nmap — port and service enumeration.

  • INFO — server and environment enumeration.
  • KEYS / SCAN — Redis keyspace enumeration.
  • GET — retrieving stored string values.
