05 — Explosion.

Very Easy · Windows · RDP

VERY EASY WINDOWS RDP ENUMERATION XFREERDP
01 — ENUMERATION

Initial service discovery

I started with a broad Nmap scan to establish the target's exposed attack surface. The goal was to identify the Windows services available remotely and determine which one should receive deeper investigation. 

nmap -sC -sV <TARGET_IP>

Initial scan identifying Windows RPC, SMB, RDP and WinRM-related services.

FINDING 01

The host exposed 135/tcp, 139/tcp, 445/tcp, 3389/tcp and 5985/tcp.

Port 135 — Microsoft RPC

TCP 135 is associated with the Windows RPC endpoint mapper. RPC allows Windows services and applications to expose remote procedures, while the endpoint mapper helps clients determine which dynamically allocated ports are associated with available RPC services.

Port 139 — NetBIOS Session Service

TCP 139 indicates SMB communication over NetBIOS. This is commonly associated with older Windows file and printer-sharing mechanisms. The simultaneous presence of 139 and 445 suggested that SMB was available through both legacy and direct TCP transport.

Port 445 — SMB

TCP 445 provides direct SMB communication without relying on NetBIOS. SMB is used for network file and printer sharing as well as other Windows remote operations, making it an important service to enumerate on Windows targets.

Port 3389 — RDP

TCP 3389 was identified as Microsoft Terminal Services, indicating that Remote Desktop Protocol was exposed. This immediately became the primary service of interest because RDP provides interactive remote access to a Windows system when valid authentication succeeds.

Port 5985 — WinRM

TCP 5985 exposed Microsoft's HTTP-based Windows Remote Management service. WinRM can provide remote management functionality, but no WinRM exploitation was required for this machine.

ATTACK SURFACE

Although several Windows services were exposed, the presence of RDP on port 3389 provided the clearest path for obtaining interactive access, so I moved to RDP-specific enumeration.

02 — RDP ENUMERATION

Fingerprinting the RDP service

I narrowed the scan to port 3389 to collect RDP-specific information and confirm that the remote desktop service was reachable. 

nmap -sV -Pn -p 3389 <TARGET_IP>

Focused enumeration of the RDP service.

FINDING 02

RDP was reachable on TCP 3389.

The deeper service output also exposed useful host metadata through the RDP negotiation process, including the machine name, NetBIOS domain name, product version and certificate information.

Host identity

The RDP fingerprint identified the target as EXPLOSION. The same name appeared in the NetBIOS and DNS computer-name fields, providing a consistent host identity.

Windows version

The RDP output reported product version 10.0.17763, placing the host in the Windows build family associated with Windows Server 2019 / Windows 10 version 1809.

Certificate information

The service also presented an RDP certificate whose subject referenced Explosion. Certificate details are useful during enumeration because they can corroborate host identity and provide additional context about how the service is configured.

03 — RDP SECURITY

Enumerating supported security mechanisms

I then used Nmap's RDP security enumeration script to determine which security protocols were supported by the server and to understand how authentication was negotiated. 

nmap -p3389 --script rdp-enum-encryption <TARGET_IP>

Enumerating the RDP security protocols supported by the target.

CredSSP / NLA

The scan reported: 

CredSSP (NLA): SUCCESS

CredSSP uses TLS to protect the authentication exchange and can use Kerberos or NTLM through SPNEGO. RDP uses CredSSP to authenticate the user and protect subsequent communication over the established TLS channel. :contentReference[oaicite:1]{index=1}

The successful NLA result confirmed that the target supported Network Level Authentication before the full interactive RDP session was established.

CredSSP with Early User Authorization

The scan also reported: 

CredSSP with Early User Auth: SUCCESS

This indicated support for the extended CredSSP negotiation that performs early authorization during the RDP connection process.

RDSTLS

The scan also reported: 

RDSTLS: SUCCESS

This demonstrated that the service supported an RDP security layer based on TLS.

SECURITY OBSERVATION

The target supported modern RDP security mechanisms, including CredSSP/NLA and RDSTLS. This confirmed that the service was not simply exposing an old unauthenticated RDP stack.

04 — SERVICE VALIDATION

Enumerating RDP configuration

With the service confirmed, I performed additional protocol-specific checks to understand the supported security configuration before attempting access. 

nmap -sV -Pn -p3389 \
--script rdp-enum-encryption,rdp-ntlm-info \
<TARGET_IP>

The combination of rdp-enum-encryption and rdp-ntlm-info provides additional visibility into the RDP security negotiation and the NTLM metadata exposed by the service. Nmap documents both scripts as safe/discovery-oriented enumeration scripts. :contentReference[oaicite:2]{index=2}

TLS configuration

I also checked the TLS configuration exposed by the service: 

nmap --script ssl-enum-ciphers -p 3389 <TARGET_IP>

This type of scan is useful for identifying the cryptographic protocols and cipher suites offered by an exposed TLS-enabled service.

Known vulnerability check

I also considered an RDP-specific vulnerability check: 

nmap --script rdp-vuln-ms12-020 -p3389 <TARGET_IP>

This checks for the historical MS12-020 RDP vulnerability. No exploitation of that vulnerability was required for this machine; the purpose of the step was to validate whether an older known RDP attack surface was present before continuing with authentication testing. Nmap documents rdp-vuln-ms12-020 as a script for checking this historical issue. :contentReference[oaicite:3]{index=3}

05 — REMOTE ACCESS

Connecting with xfreerdp

After establishing that RDP was reachable and understanding the authentication mechanisms, I moved to the RDP client to test interactive access.

With FreeRDP, the /v: option specifies the target server. 

xfreerdp /v:<TARGET_IP>:3389

The first connection attempt returned a FreeRDP crypto error. This did not mean that the RDP service itself was unavailable; the client had progressed to certificate/cryptographic handling before the attempt failed.

Initial FreeRDP connection attempt and crypto-related error.

I then retried the connection while explicitly specifying the username: 

xfreerdp /v:<TARGET_IP>:3389 /u:administrator

The client successfully progressed through the RDP negotiation and presented the Windows session.

06 — ACCESS CONFIRMED

Successful RDP session

Successful remote desktop connection to the target.

FINDING 03

Interactive Windows access was successfully established through RDP using the administrator account.

At this point the target was accessible through a normal Windows desktop session. The successful connection confirmed that the exposed RDP service, authentication path and account configuration were sufficient to obtain interactive access.

The machine therefore demonstrates an important distinction between secure protocol support and secure account configuration. The RDP service can support modern security mechanisms while still being vulnerable to improper authentication configuration.

07 — CLIENT REFERENCE

xfreerdp essentials

The FreeRDP client exposes several options that are useful when interacting with RDP during authorized testing. 

xfreerdp /v:<TARGET_IP>
xfreerdp /v:<TARGET_IP>:3389 /u:administrator
KEY OPTION

/v: specifies the destination server or IP address.

08 — AUTHENTICATION TESTING

Credential testing considerations

RDP services are commonly tested for weak credentials during authorized penetration tests. Hydra supports RDP authentication testing, for example: 

hydra -t 1 -V -f -l administrator -P passwords.txt rdp://<TARGET>

In this machine, however, a large password attack was not necessary to establish access. The practical lesson was that authentication configuration can be more important than the presence of modern protocol security features.

ASSESSMENT NOTE

Credential attacks should only be performed within authorized scope and with an appropriate rate limit to avoid account lockouts or service disruption.

09 — WHAT I LEARNED

Lessons from Explosion

Explosion reinforced the importance of moving from broad enumeration to protocol-specific analysis. The initial scan exposed several Windows services, but RDP quickly became the primary focus because it provided a direct path to interactive access.

The RDP security enumeration also demonstrated why service fingerprinting should go beyond simply identifying an open port. CredSSP, NLA, RDSTLS, certificate information and NTLM metadata provided a much clearer picture of how the remote desktop service was configured.

Most importantly, the machine showed that strong protocol support does not automatically mean that the overall system is securely configured. The authentication and account configuration ultimately determined whether the exposed RDP service could provide access.
