1. What is Wireshark?

Wireshark is an open-source network protocol analyzer. It captures packets from supported interfaces or opens saved capture files, then decodes the observed bytes into protocol fields for inspection. It is used by network engineers, incident responders, security analysts and students to understand how systems communicate. A packet list summarizes each frame; a packet-details pane expands protocol layers; and a bytes pane shows the underlying captured data. This layered view helps connect visible application behavior with Ethernet, Internet Protocol, transport protocols and application-layer exchanges. [1]

Wireshark belongs in Blue Teaming here because its main learning role is packet-level investigation and troubleshooting. It is not an intrusion verdict engine and it does not automatically explain intent. The capture only includes traffic visible to the selected interface or supplied file. When traffic is encrypted, Wireshark can often show metadata such as addresses, timing and protocol negotiation while the application payload remains unreadable. Use captures from your own host, a supplied training file or an explicitly authorized network; packets can contain credentials, cookies, personal messages or other sensitive data.

2. Why packet analysis matters

Security monitoring often begins with a question that logs alone cannot fully answer: did a client actually connect, which side closed the session, was a DNS lookup made, or did retransmissions accompany a failure? Packet analysis can help answer such questions by presenting the observed sequence and decoded fields. It can be useful when troubleshooting an application, validating a network rule, investigating a suspicious connection or explaining why a protocol session failed. The same evidence can support a defensive timeline when combined with endpoint and server logs.

Packets must be interpreted in context. A single SYN packet does not prove a completed TCP connection, a DNS request does not prove a successful connection to the returned address, and a TLS handshake does not prove that the application transaction is benign. Capture loss, offloading, asymmetric routing, NAT and monitoring-point placement affect what can be seen. Wireshark helps inspect evidence that exists in a capture; it cannot reconstruct traffic that was never collected or infer the full intent of an encrypted application by looking at ciphertext alone.

3. Where it runs and what it consumes

Wireshark is a desktop application available for major operating systems. Capturing live traffic may require packet-capture permissions, a supported driver or a capture helper, depending on platform. Opening a saved PCAP or PCAPNG file generally requires only read access to the file. The input contains frames and their timestamps; Wireshark's protocol dissectors parse recognized fields and present them as a tree. Output may include a filtered view, statistics, exported packets or a saved capture, but those outputs depend on the original capture and the analyst's filters.

Capture on the interface that actually sees the relevant traffic. A laptop with both Wi-Fi and a VPN interface may expose different conversations on each. A host-only VM network will see traffic different from a bridged adapter. A switch typically does not send every other device's unicast traffic to a random workstation port, so promiscuous mode alone does not magically reveal all network activity. Use an approved mirror port, tap or lab topology when broader visibility is required. Record the capture point, time range and limitations as part of every investigation note.

4. Capture filters versus display filters

Wireshark has two different filtering stages. A capture filter is applied while packets are collected, using the capture library's filter language. It can reduce the number of packets written to disk, which helps manage file size and sensitive data, but packets excluded during collection cannot later be recovered from that capture. A display filter is applied to an existing capture to control which packets appear in the packet list. Display filtering does not delete the hidden packets from the capture file. [1]

The syntax differs. A capture filter for TCP port 443 is commonly written as tcp port 443. A display filter for TCP port 443 uses protocol-field syntax such as tcp.port == 443. A display filter of dns shows DNS protocol packets that Wireshark recognizes. Enter a display filter in the filter bar, then press Enter or Apply; an invalid expression is normally highlighted. If a filter returns no packets, clear it and verify the field name and data availability before concluding that the traffic did not occur.

5. Getting started safely

Install the current stable release from the official Wireshark site or your operating system's trusted package manager. Review the User's Guide for current platform-specific requirements. For a first exercise, open an official or course-supplied sample capture before collecting live traffic. This avoids accidentally recording unrelated network activity and gives you a reproducible baseline. If you capture live traffic, select the right interface, define a short time window and use a narrow capture filter when suitable.

Once a capture is open, inspect the packet list, click a packet and expand the packet-details tree. Begin with a simple display filter, then clear it to compare what was hidden. Do not enable TLS decryption or load session secrets unless the lab owner has provided them and the data is yours or explicitly authorized for analysis. Treat PCAP files like logs containing potentially confidential material: store them in a controlled location, limit copies and redact data before sharing screenshots or exports. Stop capture as soon as the test objective is met.

6. Examples: TCP and DNS investigations

Start with a saved lab capture that contains a simple TCP session. Use tcp to view TCP packets, or tcp.port == 80 to focus on packets with source or destination TCP port 80. Select a packet and expand the TCP details to examine flags, sequence numbers, acknowledgment numbers and payload length. A basic TCP handshake normally begins with SYN, receives SYN-ACK and concludes with ACK. Missing packets in a capture may reflect capture loss, filtering, an asymmetric path or packets not being transmitted; do not infer a network failure from one missing segment alone.

tcp
tcp.port == 80
tcp.flags.syn == 1
dns
ip.addr == 192.0.2.10

These are example display filters. The reserved documentation address 192.0.2.10 is a placeholder and will only match if that exact address appears in your supplied capture; it does not represent observed data. A filter for SYN flags can show connection attempts, but the analyst should inspect whether the capture includes the reply and final acknowledgment. Use dns to locate DNS queries and replies, then examine query names, response codes and returned records. A query alone does not prove that resolution succeeded or that the client connected to the result.

Use Follow TCP Stream when it is appropriate for the capture and you need to group data exchanged in a TCP conversation. It can be useful for clear-text lab protocols, but encrypted TLS content generally remains opaque. Do not export or publish streams containing credentials or personally identifiable information. Prefer documenting the relevant fields and packet numbers instead of sharing full contents.

7. TLS, encryption and visibility

TLS protects application data in transit by encrypting payload contents after the handshake establishes keys. A packet capture may still show IP addresses, ports, packet sizes, timing and some handshake metadata, depending on the protocol version and ecosystem. The visible details can help establish that a TLS exchange took place, but they do not expose the HTTP path, message body or passwords carried inside an encrypted connection. Wireshark's ability to dissect an encrypted exchange depends on having authorized access to appropriate decryption secrets and on the capture containing the needed handshake data. [1]

Do not assume that a certificate name alone proves the identity or safety of the application being accessed, and do not interpret encrypted records as evidence of benign or malicious content. In a legitimate lab, a provided TLS key log may allow the investigator to decrypt their own test session, subject to tool and protocol support. Keep such secrets separate from the PCAP and delete them when no longer needed. If decryption is not available, correlate packet timing and endpoints with server, browser, DNS and endpoint logs instead of claiming to know the plaintext.

8. Interpreting evidence and common mistakes

Every capture shows only what the sensor observed. A request may be missing because it used a different interface, the capture began too late or the filter excluded it. A checksum warning may reflect network-interface offloading, where the operating system hands packets to hardware before the checksum is finalized; it is not automatically proof of a corrupted packet. A retransmission indicates that TCP sent data again, but the cause may be loss, congestion, path problems or a receiver that did not acknowledge the segment. A reset ends a connection abruptly but does not by itself establish malicious intent.

Begin with the capture's timestamp range, interface, host addresses and filter history. Check whether the file is complete enough for the question, and look at the surrounding packets instead of a single highlighted frame. Compare both directions of a flow where available. Be cautious with name resolution features that can generate extra lookups or substitute local names. Avoid exporting unneeded payload content. When preparing a report, include the filter used, the packet numbers or times supporting the conclusion, and the caveats caused by missing visibility, encryption, NAT or capture loss.

9. How Wireshark fits a defensive workflow

Wireshark complements rather than replaces centralized telemetry. A SIEM alert can identify a time range and destination worth investigating; a packet capture may clarify the protocol exchange; endpoint telemetry can show which process created the connection; and DNS or proxy logs can add naming and application context. These sources only correlate when clocks, identifiers and collection locations are understood. Packet evidence may explain whether a handshake completed or a response arrived, while endpoint logs may identify the initiating process. No one data source necessarily proves the whole story.

Keep the investigation question narrow. For example, if a client reports that a service times out, filter to the source/destination pair and inspect the TCP handshake, retransmissions and server replies. If investigating an unexpected DNS lookup, filter DNS traffic, identify the query and response, then correlate with endpoint process and resolver logs. Distinguish what is directly visible from an inference. Document the source capture and any missing segments. The goal is a defensible timeline that supports a troubleshooting or incident-response decision, not a dramatic screenshot full of packets.

10. Hands-on packet-capture lab

Use a supplied training PCAP or generate harmless traffic between your own machine and a local lab service. If capturing live traffic, select the loopback or host-only interface that sees the test, capture only a short interval and stop after the exchange. Save the capture under a non-sensitive filename. Open it in Wireshark and record the timestamp range, relevant endpoints and any capture limitation. Apply the display filters from this guide and compare the filtered view against the unfiltered capture.

  1. Find one TCP connection and identify the handshake sequence if the capture contains it.
  2. Filter for DNS and distinguish a query from a reply.
  3. Inspect a TLS handshake without claiming to see encrypted HTTP contents.
  4. Try Follow Stream only on traffic you are authorized to inspect.
  5. Record the exact filters and packet numbers that support your conclusion.
  6. Store or delete the capture according to the lab's data-handling rules.

You should be able to explain the difference between capture and display filters, identify the TCP handshake flags, find DNS query/reply evidence, state why encrypted payloads are not ordinarily readable, and list the capture's visibility limits. If a protocol is not dissected, check the supported protocol list and packet completeness before assuming the traffic is malformed.

11. Troubleshooting and next steps

If no interface appears, review platform capture permissions and official installation notes. If you see no packets, verify the selected interface, start capture before generating the traffic and remove any restrictive capture filter. If a display filter is red or invalid, check field names and operator syntax; capture and display filters are different languages. If the capture seems incomplete, check for packet drops and sensor placement, and state this limitation in the report.

Continue learning Ethernet, IPv4/IPv6, TCP state, DNS, HTTP, TLS and the difference between packet metadata and decrypted application data. The official User's Guide and filter references should be the basis for current syntax. Packet analysis becomes reliable when you pair technical understanding with careful scope, privacy-aware handling, repeatable filters and honest statements about what the evidence can—and cannot—prove.
