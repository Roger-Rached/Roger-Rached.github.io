1. What is Microsoft Sysmon?

System Monitor (Sysmon) is a Microsoft Sysinternals utility that runs as a Windows service and driver to record selected system activity into the Windows Event Log. Depending on its version and configuration, it can provide detailed records about process creation, network connections, file activity, registry changes, DNS queries and other behaviors. Security analysts use the records to build an endpoint timeline, understand how processes relate to each other and enrich investigations that would otherwise rely on a smaller set of default Windows logs.

Sysmon generates telemetry; it does not analyze events into a final incident verdict and it does not make a system secure by itself. Collection is controlled by its configuration, and some event types are disabled or filtered depending on setup. The presence of a process-creation record tells you something about process execution, not that the process is malicious. Conversely, the absence of an event does not prove that an action never happened. Analysts need the version, config, collection pipeline and endpoint context before drawing conclusions from Sysmon data.

2. Why endpoint telemetry matters

Network sensors can show that a connection occurred, but they may not identify which local process initiated it. Default application logs can omit command-line detail, parent process context or the event relationships needed to reconstruct a sequence. Sysmon can add structured endpoint evidence, including process identifiers, parent details, hashes or network fields when the relevant event types are enabled. These records can help answer questions such as which process launched a script, whether a process connected to a remote address, or whether a file or registry object changed during a timeline.

This detail must still be interpreted in context. Legitimate software installers create processes, write files and modify registry keys. An unusual parent-child relationship may be suspicious, but it can also be part of an updater or administrative script. Analysts should compare the observed behavior with baselines, user activity, software deployment records and other logs. Sysmon helps make investigations more evidence-driven, but the detection logic, collection configuration and analyst's reasoning determine whether a hypothesis is supported.

3. Event architecture and important event IDs

Sysmon's service and driver capture configured system activity and write records to the Windows Event Log. On modern Windows installations, the common location is Applications and Services Logs → Microsoft → Windows → Sysmon → Operational. Windows Event Viewer can display the records, while event forwarding or a SIEM agent may collect them for central analysis. The local event log remains useful for validating that telemetry was generated before investigating the central collection pipeline.

Some widely used event IDs include Event ID 1 for Process Create, Event ID 3 for Network Connect, Event ID 5 for Process Terminate, Event ID 11 for File Create and Event ID 22 for DNS Query. Event ID 3 network-connection logging is disabled by default according to Microsoft's Sysmon documentation, so analysts must confirm that the configuration enables it before interpreting a lack of network events. Registry activity is represented by IDs 12–14, while Event ID 2 covers a file creation-time change. Refer to Microsoft's current event reference for each ID's exact fields and behavior, as support and available fields vary by version and configuration.

4. Where and when should Sysmon be used?

Sysmon is installed on Windows endpoints where its telemetry is needed: workstations, servers, test VMs or forensic lab machines. It requires administrative rights for installation and configuration. An organization should decide which event types are useful, how much data they generate, where logs are retained and which central collection system receives them. In a personal lab, one disposable Windows VM is enough to learn how process and DNS telemetry appears in the local event log.

Sysmon does not replace native Windows Security logs, a full endpoint detection and response (EDR) product, network sensors or centralized event correlation. It is a source of endpoint telemetry that can augment those systems. Its value depends on the collection plan: if a query asks which process made a DNS request, the relevant event type must be enabled, the event must not be filtered out and the collector must retain it. A source that was never collected cannot be reconstructed afterward.

5. Installation and safe configuration

Download Sysmon from Microsoft's official Sysinternals page and check the current version. The official documentation describes accepted license behavior and install options. A basic installation from an elevated command prompt typically uses the downloaded Sysmon executable with the install switch; an approved XML configuration can be supplied when installing or updating. Review a configuration carefully before applying it. An overly broad configuration may create substantial event volume, while an overly narrow one may exclude evidence needed for investigation.

sysmon64.exe -accepteula -i
sysmon64.exe -c
sysmon64.exe -s

The first example installs Sysmon with its default configuration after accepting the license; the second displays the active configuration; the third prints the schema used to validate configuration options. Executable names and paths differ by package and architecture, so use the file you actually downloaded and verify the commands in the current official documentation. This guide does not claim to have installed Sysmon or generated these events. If a command fails, inspect elevation, download location, architecture, service state and the documented syntax for your release.

6. Reading events and following a process timeline

Open Event Viewer and navigate to the Sysmon Operational log. Filter on the event ID or a narrow time range, then inspect the event details and XML view when you need fields not shown in the default summary. Event ID 1 can show the new process, image path, command line, parent process information and identifiers useful for correlation, including a Process GUID. Event ID 5 may record process termination. The exact fields depend on event type and Sysmon version.

Build a timeline instead of treating an individual event as a verdict. For example, a process-creation event may identify a script host, a later network-connection event may associate that process with a destination, and a file-creation event may show an artifact written during the same period. Correlate timestamps, Process GUID, Process ID, image path and user context where the data is available. The Process GUID is designed to help correlate process activity more reliably than the PID alone, since PIDs can be reused. Do not assume every event contains every correlation field.

7. Practical examples: process and DNS telemetry

In a disposable Windows VM, launch a familiar application such as Notepad and locate the corresponding Process Create event if Event ID 1 is enabled. Review its image path, parent process and command line. The expected observation is a record describing the process start, but the exact field display depends on your Sysmon build and configuration. Repeat with a simple, harmless command-line utility to compare parent and child processes. Avoid running unknown programs as part of this exercise, and do not interpret an unusual process name alone as proof of compromise.

For DNS telemetry, use a benign lookup in the same lab and check for Event ID 22 if it is enabled by the configuration. The event can help associate a DNS query with process context on that endpoint, but it does not show the complete DNS response path in every case and does not guarantee that a later connection succeeded. Network-connect Event ID 3 can provide separate connection evidence when configured; remember that Microsoft's documentation states it is disabled by default. If the event is missing, confirm the active config and expected behavior before assuming the activity did not occur.

These examples are simple validation tasks rather than a real attack simulation. Record the exact time and process, note which IDs were enabled, and correlate with native event logs or a network capture only if those sources are configured and available. Do not invent a result when a test event is absent.

8. Configuration filtering, noise and limitations

Sysmon's configuration decides which events are included or excluded. Event filters can reduce noise and disk usage, but a rule that is too restrictive may remove useful process or network evidence. Conversely, enabling every possible event can produce high volume, increase storage requirements and make analysis harder. Establish a baseline in a representative lab or test endpoint, measure event volume and review which detection questions the data supports before deploying the configuration broadly.

Event availability and content depend on Sysmon version, the active config, the event source and the collection pipeline. A field may be missing because the event type does not define it, because the action was filtered out, or because an upstream collector transformed the record. A central SIEM may not receive local logs if forwarding is misconfigured. Also consider that an administrator or attacker with sufficient privileges may affect logging; Sysmon should not be treated as tamper-proof evidence in isolation. Cross-check important findings with other data sources and follow evidence-handling policy.

9. How Sysmon fits into incident response

Sysmon can complement Windows Security logs, PowerShell logging, EDR telemetry, DNS records and network monitoring. It can provide endpoint process context for a network connection, while a network sensor may provide connection metadata or packet evidence. Wazuh or another log platform may collect and analyze Sysmon records if configured, but integration is not automatic: log channels, event forwarding, parsing and field mappings must be enabled and tested. Verify that a test event reaches the central platform before relying on it during incident response.

During triage, use Sysmon to generate specific questions: what process started at the time of interest, which parent spawned it, did the endpoint log a DNS query, and is there related file or registry activity? Confirm user, host, timestamp and configuration. If a suspicious chain is found, gather the minimum additional evidence needed and preserve logs according to policy. If a record is absent, state the collection limitation and seek corroboration. Do not equate a single event ID with a complete incident narrative.

10. Hands-on Windows lab

Use a disposable Windows VM, install Sysmon by following Microsoft's current instructions, and note the version and active configuration. Confirm that the Sysmon Operational channel receives events. Launch Notepad, record the approximate time, and search for an Event ID 1 record. If your configuration includes Event ID 22, perform a benign DNS lookup and inspect the resulting record. If network-connection telemetry is part of the exercise, explicitly verify that Event ID 3 is enabled before attempting to find a connection event.

  1. Record the VM name, Sysmon version and config used.
  2. Confirm the Sysmon Operational event channel is available.
  3. Generate one harmless process-creation event.
  4. Inspect its image, parent context and identifiers.
  5. Test DNS or network telemetry only if those event types are configured.
  6. Explain any missing fields without inventing data and restore the lab to its intended state.

You should be able to find the Sysmon log, describe at least the purpose of Events 1 and 3, explain the default configuration caveat for Event 3, and distinguish a telemetry record from a detection. Keep the VM isolated and never use untrusted commands merely to create more interesting logs.

11. Troubleshooting and next steps

If Sysmon events do not appear, check that the service is running, the event channel is enabled, the active configuration includes the required event type and the action actually occurred after installation. If the event is local but absent centrally, inspect event forwarding and the collector's parsing configuration. If event volume is excessive, review filters in a test configuration first instead of disabling broad event categories in production. Confirm event definitions against the official Microsoft reference because fields and behavior may change by version.

Continue with Windows Event Log fundamentals, process trees, command-line analysis, event filtering, log forwarding and timeline correlation. Practice describing what an event directly shows and what it merely suggests. Sysmon provides useful endpoint evidence when configured and collected properly; it is not a complete security verdict, and absence of an event is meaningful only when you understand the sensor configuration and collection path.
