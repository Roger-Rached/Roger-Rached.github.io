Blue Teaming perspective: Zeek records summarize traffic visible to the sensor. Metadata is not decrypted payload content and should be correlated with other authorized evidence.

1. What is Zeek?

Zeek is an open-source network security monitor that analyzes observed network traffic and produces structured logs and events. Rather than functioning primarily as a graphical packet viewer, it applies protocol analyzers and event-driven logic to convert traffic into records that describe connections, DNS activity, HTTP metadata and other supported behaviors. Analysts use those records to investigate traffic patterns, build timelines, search for unusual activity and correlate related network events. Zeek can analyze a packet capture offline or monitor traffic from an appropriately configured live sensor.

Zeek is not a guarantee that all network activity will be visible, nor does a metadata record automatically indicate malicious behavior. The sensor sees only traffic delivered to it, protocol analyzers have limits, and encrypted payloads generally remain unavailable as plaintext without authorized decryption support. A connection record may show endpoints, duration, byte counts and connection state; it does not on its own reveal the full user intent of the application conversation. Interpret the logs as summarized evidence and correlate them with packet captures, endpoint records and application context where available.

2. Why network metadata matters

Full packet captures can be large and sensitive, while a concise structured log can make broad patterns easier to search. Zeek can record which endpoints communicated, which services were identified, DNS names requested, HTTP metadata when visible, and other protocol-specific observations. These records can help establish baselines, identify unexpected services, follow an investigation across multiple connections and support threat hunting. A unique connection identifier can sometimes be used to pivot from a connection log to associated protocol logs generated from the same observed activity.

Metadata is not the same as content. A DNS log may show the requested name and response information, but it does not prove that the application subsequently connected successfully. A connection record may show byte counts and a termination state, but it does not prove that a file was executed or a business action completed. A domain lookup may be legitimate software behavior or a suspicious beacon; the distinction requires context. Zeek helps generate searchable evidence, not a fully automatic verdict. Define what a normal baseline looks like and combine multiple fields and data sources before reaching a conclusion.

3. How Zeek analyzes traffic

Zeek receives packets from a live capture source or reads a saved capture file. It tracks connections and dispatches observed protocol activity to analyzers when the traffic provides enough information for identification. Its event-driven architecture makes protocol events available to built-in scripts and user policy scripts. Logging frameworks write records such as conn.log, dns.log, http.log and diagnostic logs when the corresponding analyzer and logging path are active. The exact available log set depends on the traffic, configuration, enabled scripts and Zeek version.

The connection log, conn.log, is a useful starting point because it summarizes both TCP and UDP connections observed by Zeek. It can contain a timestamp, connection UID, originator and responder addresses and ports, protocol, service, duration, byte and packet counts, state and history fields. Fields vary by record type and log format. The UID can help connect related transactions in other Zeek logs, but analysts still need to understand missing or optional fields. A log entry reflects what the sensor could observe and infer, not a complete view of endpoint internals.

4. Where and when should it be used?

Zeek is useful in a network monitoring environment where traffic can be mirrored or otherwise provided to a sensor, or in an offline lab where a capture file is available. It normally runs on a Unix-like system supported by the current release; consult the official installation notes for package availability and requirements. The sensor needs appropriate interface access, enough compute and disk capacity for the expected traffic, accurate time and a plan for log retention. Offline PCAP analysis is a good first step because it is repeatable and does not require monitoring a shared network.

Choose a packet analyzer when you need detailed per-frame inspection and an interactive protocol tree; choose Zeek when structured logs, cross-connection pivots and event-driven analysis are the primary objective. These tools can complement each other, but they are not substitutes. Zeek will not see traffic that does not reach the sensor, and protocol analysis may be limited by encryption or capture loss. For high-volume deployments, account for packet drops, log rotation, storage and how logs will be indexed. A dashboard or SIEM integration is a separate configuration decision, not an automatic property of running Zeek.

5. Getting started with a sample capture

Use the official Quick Start guide and its supplied sample capture to learn the basic workflow before attaching the sensor to live traffic. Install Zeek using a supported package or documented build process for your operating system. Work in a clean directory so new logs are easy to identify. The quick-start command below reads a capture file rather than starting live monitoring, and the option requests JSON-formatted ASCII logs where supported in the documented workflow.

mkdir zeek-lab
cd zeek-lab
zeek -r quickstart.pcap LogAscii::use_json=T
ls

The sample file must be obtained from the official guide or your training materials and placed in the current directory. The command processes captured traffic; Zeek typically writes log files rather than printing a summary to the terminal. The presence and content of logs depend on packets in the input file. This is an example based on the official quick-start documentation and was not executed as part of creating this page. If the command fails, verify that Zeek is installed, the file exists, the current directory is writable and the option is supported by the installed version.

6. Reading connection, DNS and HTTP logs

Start with conn.log to identify a conversation's endpoints and timing. The fields often include id.orig_h, id.orig_p, id.resp_h and id.resp_p, which describe the originator and responder addresses and ports as Zeek observed them. proto identifies the transport protocol, while service may contain an inferred service label when recognized. A connection UID can link records across logs. It is more reliable to use these fields as structured records than to parse a rendered line based only on position.

DNS logs can show query names, record types, answers and response codes when Zeek observed and decoded the transaction. HTTP logs may include method, host, URI and response information when those details are visible. HTTPS payloads are encrypted, so do not expect ordinary Zeek HTTP logs to contain full protected request paths or bodies from TLS sessions. Metadata can still show connection timing and other observable protocol characteristics, but which fields exist depends on the protocol and sensor configuration. For deeper detail, pivot to a packet capture only if the capture is available and authorized for the investigation.

When writing queries, first validate the field names against the current log schema and a sample record. A missing field may be absent because the protocol was not detected, the connection ended early or the relevant analyzer did not generate the record. Do not interpret an empty field as a definite “no” without understanding the schema and capture. Record the log source, time window and relevant identifiers so another analyst can reproduce the pivot.

7. Event-driven scripts and outputs

Zeek scripts can subscribe to events and apply policy logic, which allows teams to add local detections and enrichments. At an introductory level, think of an event as a structured notification that observed traffic or internal processing reached a defined condition. A script can inspect event arguments, apply conditions and emit an additional log or notice. Scripts should be small, documented, reviewed and tested against known traffic. The event model is powerful but depends on what Zeek observed and which analyzer produced an event.

A useful first exercise is to read the existing logs from the official sample capture before writing a custom script. Compare a connection's record with related DNS or HTTP entries using the UID where available. This teaches how records join and why one line seldom describes the complete story. When building a local script, verify the event signature and field names against the documentation for your installed release. A rule copied from an older script may fail or behave differently if types, event arguments or policy changed.

8. Limitations and common mistakes

Zeek sees the traffic delivered to its sensor. If routing is asymmetric, a mirror port is incomplete, a tunnel is not decoded or the capture dropped packets, some connections may be partial or missing. Encryption protects application payloads, which limits visibility into paths, bodies and secrets. The analyzer may not classify an uncommon or malformed protocol, and a connection log's state codes require careful interpretation. Logs can be rotated, filtered or configured with different fields, so analysts should not assume every deployment emits the same schema.

Common mistakes include treating a log line as a confirmed detection, failing to inspect missing fields, mixing timestamps without time-zone awareness, using outdated field references, and retaining logs without considering privacy. A single domain or service value is not inherently malicious. Establish baselines, look at multiple related records and correlate with endpoint data or approved packet evidence. If the sensor reports missed packets or analyzer errors, document the resulting uncertainty. A defensive report should say what Zeek observed and where visibility stops.

9. How Zeek connects to a defensive workflow

Zeek can be one layer in network detection and response. Suricata can report signature matches, Wireshark can inspect a captured conversation, and endpoint telemetry may connect network activity to a process. These tools observe different evidence and need not share data automatically. A sound workflow uses timestamps, endpoint addresses, ports and available identifiers to correlate records, then checks whether the combined evidence supports the hypothesis. Where an alert references a suspicious connection, Zeek logs can help establish related activity and likely protocol context.

Use a documented ingestion and retention plan if forwarding Zeek logs to a search platform. Validate parsing, field mappings and timestamps using sample data before relying on dashboards. Preserve the original evidence and note transformations that may alter field names or precision. When responding to an alert, describe the known source, destination, service, duration and associated records; identify any missing packet visibility or encrypted content. Avoid statements about the payload unless it was actually accessible through an authorized data source.

10. Hands-on sample-capture lab

Download the official sample capture referenced by the Zeek Quick Start guide or use a packet capture explicitly provided for training. Run Zeek against that saved file in a clean, writable directory. Inspect conn.log and note the source and destination endpoints, protocol, duration and UID for one connection. Then search the related logs for the same UID and record any associated DNS or HTTP metadata. Do not expect all protocols to have all log types; only pursue records that exist for the sample flow.

  1. Record the Zeek version and the source of the sample capture.
  2. Read the connection log and choose one record.
  3. Use its UID to search related protocol logs.
  4. Explain which fields are observed and which are inferred.
  5. Identify how encryption or capture position limits your conclusions.
  6. Keep the sample output in the lab and remove it according to course policy.

You should be able to explain how a PCAP becomes logs, what a connection UID is for, what conn.log represents, how to pivot into DNS or HTTP logs, and why metadata cannot be treated as decrypted content. For an advanced follow-up, compare one flow's connection record with the available packet evidence and note any information that one representation exposes but the other does not.

11. Troubleshooting and what to learn next

If no logs are created, check the input file path, write permissions and command output. If expected protocol logs are absent, verify that the sample contains that protocol and review the relevant analyzer configuration. If live monitoring reports packet loss, check interface access and the capacity of the sensor and host. If JSON output is required, follow the current documentation for the logging writer and configuration rather than assuming the option is identical across versions.

Continue with network protocols, DNS, HTTP, TCP state, event-driven scripting, log schemas and sensor design. Read official documentation for the current log reference and version. The core skill is turning structured metadata into a careful, testable hypothesis while acknowledging where the sensor had no visibility. Zeek strengthens an investigation when records are correlated and interpreted in context—not when a single field is treated as a verdict.
